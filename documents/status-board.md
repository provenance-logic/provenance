## Right now

**Stage:** Pre-PRD-overhaul. The OSR roadmap as previously sequenced no longer reflects reality. Stage 5 ("Pre-launch sweep") cannot honestly tag `v0.1.0-osr` while B-063 is open. The full PRD goes back to the drawing board on the 2026-05-24 weekend; this board is now a TRUTHFUL snapshot for that conversation, not a polished launch dashboard.

**Active OSR blockers:** **1** — [B-063](bugs/open.md#B-063). The connector framework advertises 12 connector types in the type system, the registration form, and the API. Only **3** have real implementations end-to-end: PostgreSQL (probe + schema), S3 (probe + schema), Databricks (probe + schema + discovery crawl + table-level lineage projection — Layers 1-4 shipped in PRs #142-#146 tonight). The other 9 (mysql, snowflake, bigquery, redshift, gcs, azure_blob, kafka, redpanda, rest_api, custom) still fall through `ConnectorProbeService.probe()`'s default branch that returns a synthetic `healthy` without doing anything. A first-time contributor registering a Snowflake or Kafka connector sees the same fakery the original B-063 filing documented. **OSR ≠ "one connector works"** — it means every advertised type does.

**Open High-severity bugs:** **0** (B-063 elevated to Blocker per the standard above).

**Open Medium-severity bugs:** **3** — B-011 (OPA amd64-only on Apple Silicon), [B-060](bugs/open.md#B-060) (last remaining piece: wire `demo-smoke-test.sh` + `seed:verify:soft-reset` into CI), [B-062](bugs/open.md#B-062) (RLS `is_local` session variable doesn't persist across pool connections — defense-in-depth gap exposed by B-061's analysis).

**Open Low-severity bugs:** **10** — B-029, B-023, B-024, B-001, B-002, B-003, B-005, B-006, B-007, B-008.

**Headline from the 2026-05-21 session.** Ten PRs merged. The arc has two halves:

*Operator tooling + tenant isolation cleanup (PRs #137–#140):*

*B-063 surfaced + Databricks integration Layers 1–4 (PRs #141–#146):*
- #141 — filed B-063 + `documents/architecture/databricks-integration-sketch.md` after realizing the connector framework is register-only beyond PG/S3.

- #145 — Layer 3b: `connectors.capability_manifests` table (V31), seeded Databricks 1.0.0 manifest, read-only service, auto-crawl on connector registration (fire-and-forget, gated on the manifest's `supports_discovery_crawl`).
- #146 — Layer 4: table-level lineage projection from Unity Catalog Lineage Tracking API into Neo4j via the existing `LineageService`. Cross-catalog edges flowed through.

**Strategic correction at end of session.** Matt: *"This is not about demos. That's part of it. But for this to be real, every single one of those connectors needs to actually work. EVERY ONE. This is not open source ready. This coming weekend, we are going back to the drawing board and overhauling the damned PRD."* The session's framing — "ship Databricks as the demo beat" — was incomplete. The platform's credibility lives or dies on every advertised capability. Three connectors implemented out of twelve is not OSR; it's a working demo path with nine pieces of fakery around it. Captured in the new feedback memory `feedback_osr_means_every_connector_real.md`.

**What this means for the board going into the weekend.** "Active OSR blockers: 0" — the headline this board carried entering tonight — was wrong by the standard above. B-063 was filed during the session and is now correctly marked as the sole open OSR Blocker. Other CLAUDE.md / PRD claims may be similarly hollow (capability manifests, discovery coverage scoring, lineage source markers, the "five non-negotiable architectural constraints," ADR claims — each is worth verifying against actual code behavior before assuming it's real). That audit is part of the weekend conversation.

## Up next (priority order)

**The biggest item is not on this list.** It's the 2026-05-24 weekend PRD overhaul. The roadmap below this section is the OLD plan from before B-063 was surfaced; it is preserved for context only. Expect the post-weekend status board to reshuffle this list substantially — possibly retire it entirely in favor of a new structure that takes the connector framework gap seriously.

In the meantime, these are the items that survive any reasonable PRD reshape:

1. **PRD overhaul session (2026-05-24 weekend).** What "OSR" actually means in light of the connector framework gap. Whether Phase 3 (claimed ✅ Complete) reopens or the phase model itself is revised. Whether the 12-connector promise is the right scope or whether OSR ships with a smaller, fully-implemented set. What other platform claims are similarly hollow. The output of this conversation reshapes everything else on this board.
2. **B-063 audit pass — does every connector type need to ship?** Real options: (a) implement all 12; (b) ship OSR with a documented smaller scope (e.g. "PG + S3 + Databricks v1, others marked Experimental"); (c) hide the registration form for unimplemented types until they're real. This is a strategy question, not a code question — answer in the weekend session.
3. **The B-060 → B-061 → B-063 pattern audit.** Three different "feature named in data model / PRD / type system but not implemented." Almost certainly more like this in the codebase. CLAUDE.md should be re-read line by line against the actual code; the PRD's "Implemented" / "Partially implemented" / "Not implemented" entries need a fresh pass. Don't trust any "✅" without verification.
4. **B-060 CI integration (last piece).** Wire `demo-smoke-test.sh` (now including the B-061 cross-org regression check) and `seed:verify:soft-reset` into a workflow that runs on every merge to main. Small, structural, prevents the next API/schema move from re-breaking either script.
5. **B-062 — RLS-by-default refactor.** Defense-in-depth for B-061. Design-pass work: per-request sticky connection, transactional wrapper, or formalize "every service query filters on `ctx.orgId` explicitly" as a lint-enforced pattern. Bigger lift, deserves its own session.
6. **B-011 — multi-arch OPA image.** Bigger jump than the entry suggests (OPA 1.x defaults to Rego v1; bootstrap policy at `infrastructure/docker/config/opa/policies/health.rego` is v0 syntax). Apple Silicon contributors run under amd64 emulation today — functional, slow.
7. **Low-severity backlog** — B-029, B-023, B-024, B-001-B-008.
